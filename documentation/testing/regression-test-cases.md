# Ручное регрессионное тестирование VBallAgregator — тест-трейсы

> **Назначение:** полный набор тест-кейсов с явными **тест-трейсами** (шаги, данные, ожидания, способ проверки) для регрессии перед релизом.  
> **Версия документа:** 2.0  
> **Дата:** 2026-05-11  
> **Охват:** команды и callback из `src/bot/modules/*`, обработчики уведомлений и планировщика (по стенду), HTTP `/health*`.

**Как пользоваться:** для каждого прогона заполняйте колонку «Факт / № билета» в своём трекере или копируйте блок «Шаблон фиксации результата» в конце кейса.

---

## Соглашения

| Поле | Описание |
|------|-----------|
| **Приоритет** | **P0** — дымовой минимум релиза; **P1** — полная регрессия; **P2** — расширенная / негатив / нагрузка |
| **Проверка** | что смотреть: ответ бота, БД, логи, HTTP, второй аккаунт Telegram |
| **Команды** | актуальны для текущего кода; отсутствующие в боте сценарии помечены «не применимо» |

---

## Шаблон тест-трейса (копировать в тикет)

```
ID кейса:
Окружение (staging / prod / local):
Версия сборки / коммит:
Исполнитель:
Дата:

Предусловия выполнены: да / нет
Шаги 1..n: OK / FAIL на шаге ___
Фактический результат:
Отклонения от ожидаемого:
Баг (ссылка):
Статус: PASSED / FAILED / BLOCKED / SKIPPED
```

---

## Подготовка к регрессии

1. Два Telegram-аккаунта: **игрок**, **организатор** (или переключение ролей по сценарию).
2. Чистая или контролируемая БД; известные `gameId`, `venueId` из сида/ручного создания.
3. Для P0: бот отвечает на `/start`; для напоминаний и очередей — **стенд** с Redis, воркером планировщика и корректным временем (или тестовые игры «в ближайшие минуты»).
4. Для API: базовый URL сервиса и доступ к `GET /health`, `GET /health/ready`, `GET /health/live`.

## Матрица приоритетов (кратко)

| Зона | P0 | P1 | P2 |
|------|----|----|-----|
| Регистрация | первичный игрок и организатор | повторный /start, уровни, выбор организаторов | — |
| Игрок | /games, /join, /leave, /my, /pay после начала | /game, callbacks, waitlist, /myorganizers | конкурентный join |
| Организатор | /newgame, /close, /payments, remind | /pendingplayers, confirm/reject, /myplayers | — |
| Настройки | — | /settings, тумблеры, /selectorganizers | — |
| Приглашения | — | respond yes/no, окно ответа | — |
| Общее | /help или /menu | палитра cmd_* | rate limit |
| Напоминания | — | ручное remind_payments_* | автоматические по времени (стенд) |
| Инфра | GET /health | ready/live | логи, негатив |

## Регистрация

### TC-REG-001 — Первичная регистрация: мультиспорт (новый пользователь)

**Приоритет:** P0  
**Предусловия:** пользователь не создан в БД (новый Telegram-аккаунт или очищенная запись).  
**Шаги:**

1. Отправить `/start`.
2. Выбрать виды спорта (`onb_t_volleyball`, `onb_t_tennis`), **«Далее»** (`onb_t_done`).
3. Демография: `onb_dg_*`, `onb_da_*` (один раз).
4. Мастер волейбола (`onbVB_*`) и/или тенниса (`tennis-profile`).

**Ожидаемый результат:** `User`, `user_sport_profiles`, `matching_*`; финал с подсказками.

**Проверка:** Prisma. **Автотест:** e2e `newUser_volleyballOnly`, `newUser_tennisOnly`.


---

### TC-REG-002 — Онбординг: «организую волейбол»

**Приоритет:** P0  
**Предусловия:** новый аккаунт; при проверке ветки без списка — нет других `Organizer` в БД.

**Шаги:** TC-REG-001 (волейбол) → `onbVB_org_yes`.

**Ожидаемый результат:** `wantsOrganizeVolleyball`; при пустом списке организаторов — summary без `select_organizers_registration`; `Organizer` создаётся при финализации.

**Проверка:** Prisma. **Автотест:** e2e `volleyball_organizer_noOthers`.

---

### TC-REG-003 — Редактирование профиля (все виды настроены)

**Приоритет:** P0  
**Предусловия:** `user_sport_profiles` для всех видов из каталога.

**Шаги:** `/start` → `onb_rp_edit` → `onb_rf_volleyball` или `onb_rf_tennis` → изменить мастер.

**Ожидаемый результат:** обновление в БД без дубликата `User`. **Автотест:** e2e `returning_editVolleyball`.

---

### TC-REG-004 — Добавление недостающего вида спорта

**Приоритет:** P0  
**Предусловия:** настроен один вид из каталога.

**Шаги:** `/start` → `onb_rp_add` → выбрать недостающий вид → `onb_t_done` → мастер нового вида.

**Ожидаемый результат:** вторая строка `user_sport_profiles`. **Автотест:** e2e `partial_addTennis`.

---

### TC-REG-005 — Выбор организаторов: сохранение и пустой выбор

**Приоритет:** P1  
**Предусловия:** игрок на шаге выбора организаторов или `/selectorganizers`.

**Шаги:**

1. Включить несколько организаторов → `organizers_done`.
2. Открыть выбор снова, снять всех → `organizers_done`.

**Ожидаемый результат:** сообщение о сохранении и корректное состояние связей (в т.ч. «все удалены», если сценарий поддерживается).

**Проверка:** БД `selectOrganizers`; тексты бота.

---

### TC-REG-006 — Регистрация без команды `/cancel`

**Приоритет:** P2  
**Примечание:** отдельной команды `/cancel` в модулях бота нет. Проверить только поведение при прерывании диалога (закрытие чата, игнор callback). Ожидания зафиксировать по факту: частичные данные не должны ломать повторный `/start`.

## Процесс регрессии

1. Выполнить все **P0** на целевом окружении.  
2. Выполнить **P1** для полного регресса.  
3. **P2** — по времени, после изменений в области или раз в N релизов.  
4. В отчёте указать: процент PASSED, список FAILED с билетами, BLOCKED с причиной (нет стенда, нет команды).
